## 0. 개발 방향 (2026-09-29 교수님 피드백 반영 · 10-01 갱신)

> 아래가 현재 개발 기준이다. 1~9절은 공모전 제출용으로 정리한 아이디어 서술이라 AI 판별을 주 기능으로 쓰고 있으니, 개발 범위는 이 절을 따른다.

### 0-1. 확정 사항

- A안(EdgePdM)을 중단하고 **PolaGrid 단독**으로 진행한다. EdgePdM 문서는 `EDGE_PDM_B/`에 보관.
- CSE는 **tinyIoT 계층 구조**로 정한다(10-01, 09-29의 Mobius 결정을 변경). 구역마다 엣지(MEC)에 MN-CSE를 두고 칸을 나눠 맡기며(예: MN 10개 × 100칸), IN-CSE도 tinyIoT. Mobius IN은 서로 다른 구현체 간 상호운용성 시연·대체용, ACME는 제외(최대 78 req/s).
  - 근거: 2026 대회는 6th oneM2M International Hackathon 겸 ESTIMED Hackathon #2("Building a Scalable Cross Industry Solution by Bridging IoT and Edge", oneM2M + ETSI MEC 필수, ACME·tinyIoT·Mobius + MEC Sandbox 허용). 과거 수상작은 실물 양방향 제어와 최신 표준 기능 활용이 공통점.
  - 확정 관문(Week 0): MN 1개에 100칸, 구역 명령 p95 ≤ 5s. 실패하면 IN을 Mobius로 바꾸고 MN 유지 여부를 다시 판단.
- 팀은 **1인**(기획·하드웨어·AI·플랫폼 전부). 과기정통부 AI 활용 아이디어 공모전 신청서는 v3로 제출 완료.
- 상세 계획(7주 일정, 약 78시간): `PolaGrid_계획서_V2.md`

### 0-2. 피드백과 대응

| 피드백 | 대응 |
|---|---|

| 실물 1~2개 + 가상 시뮬레이터 | 실물 2칸과 가상 N칸을 같은 리소스 트리에 올림 |

### 0-3. 시뮬레이션 방향 (상세: `PolaGrid_시뮬레이션_활용성_검토.md`)

- 대규모 트래픽 처리 검증과 관리·제어 검증 둘 다 쓸모가 있다. 단, 칸이 명령에 반응하는 **폐루프**로 만들어야 관리·제어 쪽까지 검증된다.
- 트래픽: 칸 수에 따른 지연·처리량 곡선은 실물로는 만들 수 없는 결과물이다. 1만 칸이 조도를 60초마다 보고하면 약 167 req/s가 필요하다(가정 기반 계산).
- 관리·제어: 시뮬레이터로만 가능한 검증 4가지 — 같은 날씨를 반복 재생하는 알고리즘 회귀 테스트, zone 단위 일괄 조작, 장애 주입, 1만 칸에서 이상 칸을 찾는 관측.
- 설계: 물리 모델과 oneM2M 통신부를 분리한다.
- 도구: 부하 생성은 Locust 채택, 폐루프 시뮬레이터는 직접 구현, frads(Radiance+EnergyPlus)는 채광·눈부심 물리 모델 오프라인 검증 후보, oneM2M 전용 시뮬레이터·oneM2MTester는 보조, Eclipse Ditto는 oneM2M 필수 조건에 맞지 않아 제외.

### 0-4. 부하 측정 결과 (ACME 2026.05.1, 로컬 PC 8코어·8GB, 원본 `results/`)

1차, 칸 수 증가(기본 설정, 칸마다 AE):

| 칸 수 | 처리량 | CIN 응답 p95 |
|---|---|---|
| 10 | 175 req/s | 41 ms |
| 100 | 137 req/s | 122 ms |
| 1,000 | 36 req/s | 1,344 ms |

2차, 설정 × 구조 비교(칸 1,000개 설치 후 CIN 3,000건, 운영 처리량):

| 설정 | 칸마다 AE | zone마다 AE |
|---|---|---|
| 기본 (tinydb) | 10 req/s | 7 req/s |
| 로그 off | 12 req/s | 8 req/s |
| 메모리 DB + 로그 off | **78 req/s** | 72 req/s |

- **저장소(tinydb)가 병목이다.** 로그 끄기는 효과가 없다. zone마다 AE는 성능 이득이 없으므로 구조는 관리 편의로 고른다.
- 부하 중 ACME CPU가 코어 1개 100%에 고정됐다. 1,000칸(약 17 req/s 필요)은 가능하고, 1만 칸(약 167 req/s 필요)은 ACME로 불가능하다.
- 이 수치는 ACME의 한계다. **발표용 수치는 Mobius에서 다시 측정한다.** 조합당 1회 측정이고 클라이언트와 CSE가 같은 PC에서 돌았다.
- Locust 동작 확인: 칸 50개, 조도 5초 주기, 45초 실행, 실패 0건.

### 0-4c. tinyIoT MN 측정 (2026-10-01, WSL Ubuntu-24.04, i7-1195G7 8스레드 / WSL 7.8GB, 원본 `results/*_1001.txt`)

조건은 ACME 2차와 같다(칸 1,000개 설치 후 CIN 3,000건, 동시 20). 대상은 MN-CSE 1개(`TinyIoT-mn001`, SQLite).

| 저장소 설정 | 칸마다 AE 운영 처리량 | zone마다 AE | CIN p95 (칸마다 AE) | CSE CPU 최대 |
|---|---|---|---|---|
| 기본(SQLite, 커밋마다 fsync) | 69 req/s | 49 req/s | 330 ms | 7% |
| tmpfs(진단용, 디스크 I/O 제거) | 690 req/s | 230 req/s | 35 ms | 27% |
| **WAL + synchronous=NORMAL 패치** | **577 req/s** | 190 req/s | 42 ms | 17% |

구역 명령 전달(`tools/fanout_test.py`, 칸 100개, 칸마다 command CNT + SUB, 20회, 명령 POST → 100칸 모두 알림 도착까지):

| 저장소 | GRP fan-out 1회 | 칸마다 개별 POST(동시 20) |
|---|---|---|
| 기본 | p50 1,637 ms / p95 2,655 ms | p50 2,755 ms / p95 5,333 ms |
| WAL 패치 | **p50 106 ms / p95 151 ms** | p50 1,086 ms / p95 2,125 ms |

- **Week 0 관문(MN 1개 · 100칸 · p95 ≤ 5s) 통과.** WAL 패치 + GRP fan-out에서 p95 151 ms.
- 기본 설정의 병목은 CPU가 아니라 SQLite 커밋마다의 디스크 동기화다(CPU 7%, tmpfs에서 10배). WAL 패치로 ACME 최대치(78 req/s)의 약 7배.
- zone마다 AE 구조는 tinyIoT에서도 이득이 없다(ACME와 같은 결론).
- 한계: 1회 측정, 클라이언트·CSE 같은 PC, 기본 설정 fan-out은 앞선 1,000칸 측정 자원이 남은 DB에서 잼(WAL은 새 DB).
- 측정 중 tinyIoT 버그 2건 추가 발견(`sim/README.md`): GRP fan-out으로 만든 자원에 구독 알림이 안 감(패치함), 멤버 100개 GRP가 있으면 재시작 시 stack smashing으로 죽음(40개는 정상, 미수정).

### 0-4d. 1,000칸 계층 측정 (2026-10-01, 같은 PC·WSL, 원본 `results/scale_curve_tinyiot_1001.txt`)

MN-CSE M개 × 칸 100개, 구역(MN)마다 GRP 1개, 칸마다 command CNT + SUB. 명령 1회 = M개 구역에 동시에 GRP fopt → 모든 칸에 알림이 도착할 때까지. 10회, 단계마다 새 DB, 알림 수신기는 구역별 별도 프로세스(`tools/hier_test.py`, `tools/run_scale_curve.sh`).

| MN × 칸 | 엣지에서 직접 (p50 / p95) | IN 경유 (p50 / p95) | 시스템 CPU 평균 / 최대 |
|---|---|---|---|
| 1 × 100 | 95 / 154 ms | 187 / 207 ms | 6% / 38% |
| 2 × 100 | 126 / 180 ms | 233 / 285 ms | 10% / 38% |
| 5 × 100 | 187 / 269 ms | 369 / 438 ms | 20% / 100% |
| **10 × 100 = 1,000칸** | **349 / 382 ms** | **676 / 801 ms** | 34% / 100% |
| 10 × 100 + 배경 조도 17 req/s | 335 / 461 ms | 672 / 731 ms | 32% / 100% |

- **1,000칸 통과 기준(p95 ≤ 5s) 통과.** 엣지 직접 382 ms, IN 경유 801 ms. 알림 누락 0 / 10,000.
- IN 경유는 엣지 직접의 약 2배 지연 → "구역 제어는 엣지(MEC)에서" 설계의 수치 근거.
- MN 수를 10배로 늘려도 지연은 약 2.5배(154 → 382 ms). MN이 한 PC에 몰려 CPU 최대치가 100%에 닿은 상태라, MN을 별도 기기에 두면 더 줄 것으로 본다(미측정).
- **주의: 이전 측정 자원이 쌓인 DB(MN당 수천 개 AE·SUB)에서는 같은 1,000칸이 p95 7.8초(배경 부하 17 req/s에서 10.5초), 배경 170 req/s에서는 MN이 30초 응답 없음.** 새 DB와 10~20배 차이. 원인(자원 수에 비례하는 탐색 등)은 미확인 → 칸 상태가 오래 쌓이는 장시간 운영 측정이 필요(`results/hier_tinyiot_1001.txt` 앞 세 블록).
- 처음엔 측정 클라이언트(파이썬 한 프로세스) 병목을 의심해 수신기를 구역별 프로세스로 나눴으나, 오래된 DB에서는 오히려 느려졌다(`results/hier_tinyiot_1001_singleproc.txt`). 결론을 가른 건 DB 상태였다.
- IN 경유 fopt가 오래된 DB에서 가끔 404를 돌려주면서도 실제 전달은 됨(새 DB에서는 200). 원인 미확인.

## 1. 배경 — 무슨 불편을 푸나

해가 드는 오후에 창가에서 공부하거나 일하면 책과 모니터에 빛이 반사되어 글자가 잘 보이지 않는다. 블라인드를 내리면 눈부심은 사라지지만 방이 어두워져 낮에도 조명을 켜게 되고 창밖도 보이지 않는다. 해가 움직이면 다시 올리고 내려야 해서 하루에도 여러 번 반복되고, 창가까지 움직이기 어려운 고령자에게는 더 큰 부담이다. 조도센서나 예약 시간으로 움직이는 전동 블라인드도 방 전체의 밝기만 보기 때문에, 방은 적당히 밝은데 책상 한쪽에만 빛이 꽂히는 상황은 잡지 못한다. 눈부심은 빛의 양보다 어디에 어떻게 비치는지에 달려 있어서 지금까지는 사람이 직접 보고 판단해야 했다.

## 2. 아이디어 — 무엇을 만드나

창 안쪽에 편광 필름 모듈을 격자로 붙이고 칸마다 작은 서보모터로 각도를 바꾼다. 편광 필름 두 장을 겹치고 한 장을 돌리면 통과하는 빛의 양이 각도에 따라 연속으로 달라진다. 책상이나 화면에서 반사되어 눈으로 오는 빛은 진동 방향이 한쪽으로 치우쳐 있어서, 창을 지나는 빛의 진동 방향을 바꾸면 같은 밝기에서도 반사되는 양이 달라진다. 실내 카메라와 조도센서가 책상 쪽을 보다가 눈부심이 생기면 그 빛이 들어오는 칸만 어둡게 돌리고, 나머지는 열어 두므로 방은 밝고 창밖도 보인다. 사용자는 앱에서 "책상 눈부심 줄이기", "화면 반사 줄이기", "최대한 밝게" 중 하나만 고르면 된다.

블라인드처럼 빛을 **차단**하지 않고 편광으로 **선택적 감쇠**하는 점이 기존 전동 블라인드·스마트 블라인드와의 차별점.

## 3. 동작 구조

```
카메라·조도센서 ──(밝기 분포)──▶ 기기 안 AI ──(어느 칸을 돌릴지)──▶ 각도 결정 ──(회전각)──▶ 편광 모듈 격자
      ▲                                  ▲                                              │
      └───────── 돌린 뒤 결과 재확인 ─────┘                                              │
                                          │                                               │
                                     모드 선택                                             │
                                          │                                               │
                                       사용자 앱 ──(보정 기록)──▶ 선호 기록 ──(선호 반영, 시간대·바깥 밝기별)──▶ 기기 안 AI
```

전부 **창가 기기 안에서만 처리**하고 영상은 저장·전송하지 않는다.

- **AI가 하는 일**: 눈부심의 유무·세기·위치를 판별 / 어떤 칸이 어느 자리에 빛을 보내는지 학습 / 보정 기록으로 선호 밝기를 학습.
- **사생활 보호**: 영상은 기기 안에서만 처리, 얼굴 없이 저해상도 밝기 정보만 사용, 카메라 없이 조도센서만 쓰는 모드 제공.
- **이미 만든 부분**: 조도센서 + 서보모터 + 편광필름 회전 장치 (2025-1 창의SW기초설계 수업 프로젝트에서 동작 확인).

## 4. 디바이스 제작 방법

모듈 한 칸은 고정 편광판, 회전 편광판, 이를 돌리는 서보모터와 기어, 창에 붙이는 프레임으로 이루어진다. 창유리를 고치지 않고 안쪽에 프레임만 부착하며 창 크기에 맞춰 칸 수만 조정한다. 제어 유닛에는 소형 리눅스 보드와 카메라, 조도센서를 넣고 다채널 PWM 드라이버로 칸마다 서보를 개별 제어한다.

## 5. IoT 플랫폼 연동 (양식에서 요구할 경우)

> `PolaGrid_계획서.pdf`(생활속 AI 공모전용)는 이 계층을 뺀 버전이다. IoT 플랫폼 연동을 요구하는 양식에 제출할 때만 아래를 추가한다.

게이트웨이는 센서값과 칸 상태를 IoT 플랫폼에 등록하고 구독과 알림으로 제어 명령을 받는다. 자원은 설치 장소와 창, 칸 단위로 나눈다.

```
/polagrid/site/{room}/panel{N}/
  ├─ lux       (조도 측정값)
  ├─ glare     (눈부심 판별 결과: 위치·세기)
  ├─ angle     (현재 편광판 각도)
  └─ command   (목표 각도 또는 모드 변경)
```

앱은 기기에 직접 접속하지 않고 플랫폼 API로 상태를 조회하고 명령을 쓴다. 사용자가 집 밖에 있어도 동작하고, 창이 여러 개인 현장이나 건물 전체로 늘려도 앱을 고치지 않아도 된다. 표준 자원으로 쌓이므로 스마트홈 허브나 건물 관리 시스템 같은 다른 응용도 같은 데이터를 읽어 쓸 수 있다.

## 6. AI 판별 모델

판별과 각도 결정은 창가의 기기 안에서 한다. 눈부심은 실시간으로 바뀌어 왕복 지연을 줄여야 하고, 영상이 밖으로 나가지 않아야 하기 때문이다. 카메라 영상에서 밝기 특징값을 뽑아 눈부심의 유무와 세기, 위치를 판별하며, 경량 분류 모델과 MobileNetV2 전이학습 모델의 정확도와 속도를 비교해 기기에서 쓸 모델을 고른다. 어떤 칸이 어느 자리에 빛을 보내는지는 칸을 하나씩 돌려 보며 기록해 학습한다. 사용자가 앱에서 고친 밝기는 시간대와 바깥 밝기별로 플랫폼에 쌓여 다음 판단에 반영된다. 카메라를 원하지 않는 현장에는 책상 위 조도센서 여러 개만으로 판단하는 모드를 제공한다.

> 규칙 기반(임계값)만으로는 "AI 서비스"로 보기 어려우므로, 눈부심 판별과 개인 선호 학습을 AI 역할로 명시할 것.
>
> 개발 범위는 0-2절 기준: 제어는 태양 위치 모델 + 조도 피드백 + 누적 통계 룩업이 주이고, 위 AI 판별은 선택 항목이다. 공모전 제출 문서에서만 AI 판별을 주 기능으로 서술한다.

## 7. 타겟 / 적용 확장

- **기관 단위**: 공공건물·학교 창호 개선 사업의 채광 자동 조절 장치.

## 8. 기대 효과 / 한계

**사회적 효과.** 창가에서 공부·일하는 사람의 블라인드 조작이 줄고 눈의 피로가 준다. 고령자·거동 불편자도 도움 없이 창가 밝기를 맞출 수 있다. 학교·도서관의 자리별 눈부심 문제를 칸 단위로 해결.

**경제적 효과.** 창을 가리지 않고 눈부심만 줄이므로 낮 조명 사용 시간이 줄고, 여름 냉방 부담도 필요한 구역만 줄여 덜 수 있다. 모듈 단위라 눈부심이 자주 생기는 구역에만 부분 도입 가능, 초기 비용이 낮다. **절감량은 측정하지 않고서는 제시하지 않는다** — 시연 단계에서 사용 전후 책상 밝기·눈부심 면적·조명 점등 시간을 직접 재서 확인.

**한계.** 편광 필름은 빛을 일부 흡수해 칸을 가장 밝게 열어도 맨 유리창보다는 어둡다 → 눈부심이 자주 생기는 구역에만 부착. 편광 필터는 수평면 반사광 감쇠에 유효하나 직사광에는 한계가 있음(제출 자료에 스스로 명시할 것).
