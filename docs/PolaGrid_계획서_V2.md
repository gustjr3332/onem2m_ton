## 1. 한 줄 정의

> 창 한 칸을 제어하는 장치가 아니라, **건물 전체 창의 편광 모듈 수천 개를 oneM2M 표준 리소스로 묶어 태양 움직임에 맞춰 동시에 최적 제어하는 IoT 플랫폼 응용.**

- 실물 2칸: 물리 동작·보정 데이터의 근거.
- 가상 수십~수만 칸: 플랫폼이 규모를 감당함을 보이는 근거.
- 공모전 평가 기준(oneM2M/MEC 표준 활용, 생태계 기여)에 맞춰 **AI가 아니라 플랫폼이 주인공**.

## 2. 무엇이 바뀌고 무엇이 그대로인가

| 항목 | 그대로 | 바뀜 |
|---|---|---|
| 하드웨어 | 조도센서 + 서보 + 편광필름 2장(고정+회전) | 실물 1칸 → **2칸**, 창 프레임 모듈화 |
| 핵심 가치 | 차단이 아닌 편광 선택적 감쇠 | 단말 1개 → **다수 칸 동시 제어** |
| 판단 로직 | 눈부심 위치 기반 칸 선택 | 카메라 AI → **태양 모델 + 조도 피드백 + 통계 룩업** |
| 플랫폼 | (v3에서는 없음) | oneM2M MN-CSE/IN-CSE + MEC Mp1 필수 |
| 시연 | 프로토타입 영상 | **스케일 시연 + 리얼/가상 혼합 대시보드** |
| EdgePdM | - | 폐기(보관) |

## 3. 아키텍처와 리소스 트리

```
[실물 칸 ×2: Arduino/ESP + 조도센서 + 서보]     [가상 칸 ×N: simulator (asyncio)]
        │ oneM2M HTTP                                   │ oneM2M HTTP
        └───────────────┬───────────────────────────────┘
                        ▼
              [MN-CSE (Docker, ACME 우선)]  ◀── 벤치마크 후 tinyIoT 대체 판단
                 │  Subscription/Notification
                 ▼
     [MEC 제어 앱: zone 단위 최적화 루프, Mp1에 polagrid-daylight 등록]
                 │  command (GRP fan-out)
                 ▼
            각 칸 angle 변경
                 │
      [대시보드]  [BMS mock 앱: 같은 데이터를 다른 목적으로 읽음]
```

리소스 트리 (실물과 가상이 동일 구조):

```
/polagrid/site/{siteId}/
  ├─ env/
  │    ├─ sun        (태양 고도·방위, 외부 조도)
  │    └─ weather    (선택)
  └─ zone{Z}/
       ├─ grp_all              (GRP: zone 내 모든 panel, 명령 fan-out용)
       ├─ desk{M}/lux          (책상 위 조도, 눈부심 평가 기준점)
       └─ panel{N}/
            ├─ lux        (창 안쪽 조도)
            ├─ angle      (현재 각도, 변경 시에만 CIN 기록)
            ├─ command    (목표 각도 또는 모드)
            └─ meta       (kind=real|virtual, 위치, 방향, 펌웨어)
```

설계 원칙
- **변화가 있을 때만 쓴다**: angle은 값이 바뀔 때만 CIN 생성. 1만 칸에서 주기 폴링하면 CSE가 먼저 죽는다.
- **명령은 zone 단위로**: 개별 command 1만 건 대신 zone 단위 GRP fan-out을 쓰고, fan-out 지연을 측정한다.
- **대시보드는 batch 알림**으로 받는다. (ACME/tinyIoT의 batchNotify·rate limit 지원 여부는 Week 0에 확인)
- 앱(대시보드, BMS mock)은 장치에 직접 접속하지 않고 **CSE API만** 쓴다 → "표준 자원으로 쌓이면 다른 응용이 그대로 재사용" 시연.

## 4. 제어 로직 — AI 없이 최적화를 각인시키는 방법

### 4.1 목적함수

zone의 각 책상 위치 m, 각 칸 각도 θₙ에 대해

- 눈부심 지수 G(m) : 태양 방위·고도, 칸 위치·방향, 책상 위치로 계산한 직·반사광 세기의 임계 초과분
- 채광 유지 조건 : 책상 조도 L(m) ≥ L_min (조명 없이 작업 가능한 최소 조도)
- 편광 감쇠 모델 : 투과량 T(θ) = T_max · cos²(θ) (Malus 법칙, 실물 보정)

```
minimize   Σ_m G(m)  +  λ · Σ_n |θₙ(t) − θₙ(t−1)|     # 눈부심 + 서보 움직임(수명·소음) 페널티
subject to L(m) ≥ L_min  for all m
```

### 4.2 제어 방식 (전부 결정적, 설명 가능)

1. **태양 모델 피드포워드**: 시각·위치로 태양 고도·방위를 계산하고 칸별 예상 눈부심 방향에 미리 각도를 배정.
2. **조도 피드백 보정**: 책상 조도(desk lux)가 목표를 벗어나면 해당 칸 각도를 소폭 조정 (PI 수준).
3. **통계 룩업(교수님 말씀의 "통계성")**: 누적된 (시간대, 외부 조도, 계절) → 최적 각도 표를 CIN 기록에서 만들어 다음 날 초기값으로 사용. 표는 `/polagrid/.../angle` 히스토리에서 재생성 가능해야 한다 → **플랫폼 데이터 활용 사례**가 된다.

### 4.3 비교 baseline (최적화를 수치로 각인)

| 방식 | 설명 |
|---|---|
| B0 고정 개방 | 각도 고정, 아무것도 안 함 |
| B1 블라인드형 | 눈부심 감지 시 zone 전체를 닫음 (기존 전동 블라인드) |
| B2 시간 예약 | 시각표대로 각도 변경 |
| **PolaGrid** | 4.2의 1+2+3 |

측정 지표: 눈부심 발생 시간(glare-hours), 평균 책상 조도, 조도 부족 시간(조명 켜야 하는 시간의 프록시), 서보 이동 횟수, 명령 전달 지연.
※ 전력·냉방 절감량은 실측 없이 주장하지 않는다 (v3 방침 유지). 시뮬레이션 결과는 "모델 기반 추정"으로 명시.

### 4.4 AI의 위치 (선택, 기본 제출본에 넣지 않음)

- 눈부심 판별(경량 분류)과 개인 선호 학습은 **Week 6 이후 여유가 있을 때만** 부가 실험으로 추가.
- 제출 서술: "제어는 결정적 모델 + 통계로 충분하며 AI는 선택적 확장." 교수님 지적과 일치시킨다.
- 카메라를 빼면 사생활 이슈도 함께 사라져 서술이 단순해진다.

## 5. 대규모 가상 시뮬레이터 (핵심 차별점)

### 5.1 구성
- 프로세스 1개가 asyncio + httpx로 수백~수천 칸을 호스팅. 각 칸은 실물과 같은 트리(lux, angle, command, meta).
- 환경 입력: 태양 위치 모델 + 날씨 노이즈 + 구름 이벤트(급변 스트레스).
- 시뮬레이션 시계 배속(1일을 10분 등)으로 하루 시나리오를 시연.
- 칸 모델: 방향(창 방위), 층, 위치 → 칸마다 태양 입사 조건이 달라 **제어가 의미 있게 갈리도록** 한다. (전부 같은 값이면 스케일 시연이 무의미)

### 5.2 스케일 단계

| 단계 | 칸 수 | 예 | 확인할 것 |
|---|---|---|---|
| S1 | 10 | 방 1개 | 기능 정상, 실물 2 + 가상 8 혼합 |
| S2 | 100 | 층 1개 | zone fan-out, 대시보드 히트맵 |
| S3 | 1,000 | 건물 1동 | 등록 시간, 지연 p50/p95, 메모리 |
| S4 | 10,000 | 캠퍼스 | 한계 탐색: 어디서 무너지는지 자체가 결과 |

### 5.3 결과물 (그래프)
- 칸 수 vs 명령 전달 지연 (p50/p95)
- 칸 수 vs CSE 처리량(req/s)·메모리
- MEC vs Cloud 위치별 제어 루프 지연
- 한계 지점에서의 완화책 적용 전/후 (변화 시에만 기록, GRP fan-out, batch 알림)

### 5.4 리스크 (솔직하게)
- **ACME-oneM2M-CSE가 1만 AE를 감당하지 못할 수 있음.** ACME는 교육용 구현이다. Week 0에 1,000 AE 등록 스모크 테스트로 ACME/tinyIoT를 먼저 판정한다. 1만 칸은 "칸당 AE" 대신 "zone당 AE + 칸당 container"로 대체할 수 있고, 이 경우 구조 차이를 문서에 명시한다.
- 시뮬레이터의 눈부심 모델은 단순화된 가정이다. 실물 2칸의 측정(각도 vs 투과 조도)으로 Malus 곡선을 보정하고, 모델 한계를 문서에 적는다.

## 6. 실물 장비 (1~2칸)

- 칸 1: 기존 2025-1 프로토타입 재가동 (조도센서 + 서보 + 편광필름 회전) + 통신 보드(ESP32 권장, WiFi로 oneM2M HTTP 직접 전송 가능하면 게이트웨이 생략).
- 칸 2: 동일 부품으로 추가 제작. 서로 다른 방향(예: 창 좌/우)에 두어 **칸마다 다른 각도가 나오는 장면**을 실물로 확보.
- 역할: (a) cos² 투과 곡선 실측 → 시뮬레이터 보정, (b) 대시보드에서 "이 칸은 실물"이 표시되고 손으로 조도를 가리면 실제로 각도가 바뀌는 시연, (c) 실물/가상이 같은 플랫폼 API를 쓴다는 증거.
- 부품 주문(추가분): 서보 1~2개, 편광 필름, ESP32 1~2개, 조도센서(BH1750 등) 2~3개. 약 3~5만원 추정(가격 미확인).
