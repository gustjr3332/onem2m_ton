# PolaGrid 가상 시뮬레이션 활용성 검토

> 2026-09-29 / `PolaGrid_계획서_V2.md` 5절의 후속. 질문: 가상 시뮬레이터가 (A) 대규모 트래픽 처리 검증, (B) 관리·제어 검증에 실제로 쓸모가 있는가.
> 전제: 신청서는 PolaGrid 이전 버전(v3)으로 제출 완료.

## 결론

**둘 다 쓸모 있다. 단, 시뮬레이터를 "부하 생성기"로만 만들면 (A)만 얻고 (B)는 잃는다.** 물리 모델(태양·눈부심)과 oneM2M 통신부를 분리하고, 칸이 명령에 실제로 반응하는 **폐루프**로 만들어야 둘 다 나온다.

| | (A) 대규모 트래픽 처리 | (B) 관리·제어 |
|---|---|---|
| 증명하는 것 | CSE·MEC가 N칸 규모에서 버티는가, 어디서 무너지는가 | 제어 알고리즘이 다수 칸에서 목적함수를 줄이는가, 운영 조작(일괄 명령·장애)이 표준 자원으로 가능한가 |
| 필요한 시뮬레이터 | 프로토콜 클라이언트 (가볍고 많이) | 물리 모델 + 폐루프 (칸이 각도에 반응) |
| 공모전 평가 연결 | oneM2M/MEC 표준 활용, 규모 근거 | 생태계 기여(재사용 앱, 튜토리얼) |
| 가장 큰 약점 | "가짜 트래픽" 지적 | "모델이 현실과 다르다" 지적 |
| 활용성 | 높음 | 높음 (조건부) |

## A. 대규모 트래픽 처리

### 부하 산정 (내 계산, 가정 명시)
가정: 1만 칸, 칸당 조도 1회/60초 보고, 각도는 변경 시에만 기록, 낮 시간대 칸당 각도 변경 약 5분에 1회.

| 트래픽 | 계산 | 요청률 |
|---|---|---|
| 조도 CIN | 10,000 / 60s | 약 167 req/s |
| 각도 CIN(변경 시) | 10,000 / 300s | 약 33 req/s |
| 대시보드 알림 | batch 없으면 위 합계만큼 | 약 200 notify/s |
| zone 명령 fan-out | 100칸 zone × 1회/5분 → 명령 100건 | 순간 버스트 |

- 주기를 10초로 좁히면 조도만 1,000 req/s. 이 지점이 교육용 CSE의 한계일 가능성이 크다.
- 설계 결론: **변화 시 기록 + batch 알림 + GRP fan-out** 3개가 없으면 1만 칸은 표준 API로 감당하기 어렵다고 보고 시작한다. 이 3개가 "IoT 플랫폼 활용" 서술의 실제 내용이 된다.

### 조사 결과 (근거 수준 주의)
- ACME는 AE 등록이 많을 때 성능이 개선됐다는 릴리스 기록이 있으나, **공개된 정량 벤치마크(몇 AE, 몇 req/s)는 찾지 못했다.** tinyIoT는 엣지용 경량 구현이라고 소개된다. 즉 "ACME가 1만 칸을 버틴다/못 버틴다"는 근거가 없고, **직접 측정해야 한다.**
- Docker 데몬이 현재 꺼져 있어 오늘은 측정하지 못했다. Docker Desktop을 켜야 한다.

### 활용 가치
- (+) 규모 곡선(칸 수 vs 지연·처리량)은 실물로는 절대 못 만드는 결과물이다.
- (+) MEC vs Cloud 지연 비교(계획서 W6)를 규모별로 반복할 수 있다.
- (−) 시뮬레이터 클라이언트가 같은 PC에서 돌면 측정이 오염된다. 클라이언트 CPU 포화와 CSE 포화를 구분해야 한다. 지표로 클라이언트 측 CPU와 요청 대기시간을 같이 기록한다.
- (−) 이번 테스트는 로컬 단일 머신이므로 "WAN 지연 하의 규모"는 주장하지 못한다. 결과 문서에 한계로 적는다.

## B. 관리·제어

시뮬레이터로만 가능한 검증 4가지:
1. **제어 알고리즘 회귀 테스트**: 같은 하루 시나리오(맑음/구름 급변)를 배속으로 반복 재생해 baseline 대비 눈부심·조도 부족 시간을 비교. 실물은 같은 날씨를 재현할 수 없다.
2. **일괄 관리 조작**: zone 전체 모드 변경, 특정 방향 칸만 정지, 설정값 롤아웃이 GRP·구독으로 가능한지. (oneM2M의 mgmtObj/firmware 리소스 지원 여부는 사용 CSE에서 확인 필요)
3. **장애 주입**: 칸 5% 오프라인, 명령 지연·유실, CSE 재시작 후 복구. 관리 제어에서 가장 중요한데 실물로는 수십 개가 없어서 시연이 불가능하다.
4. **관측성**: 1만 칸에서 이상 칸을 대시보드가 찾아내는가(오프라인, 각도 정체).

한계:
- 폐루프가 아니면 (B)-1은 무의미하다. 시뮬레이터는 command를 받아 각도를 바꾸고, 그 각도로 조도를 다시 계산해 보고해야 한다.
- 눈부심 모델은 단순화한 가정이다. 실물 2칸 측정으로 투과 곡선만 보정할 수 있고, **눈부심 지수 자체는 검증되지 않은 모델**이다. 결과는 "모델 기반 추정"으로만 표기한다.
- 각도 이동 시간(서보 속도), 통신 실패율은 실물에서 측정한 값을 시뮬레이터에 넣어야 현실감이 생긴다.

## 시뮬레이터 설계 결정

```
[Physics core]  태양·눈부심·투과(cos²)   ← 순수 함수, 프로토콜 무관
      │
 ┌────┴───────────────┐
 [Headless runner]    [oneM2M adapter]
 CSE 없이 초고속        칸당 AE, CIN, SUB, 명령 수신
 알고리즘 회귀 (B-1)    부하·장애·관리 검증 (A, B-2~4)
```

- 물리 코어와 통신부를 분리하면 알고리즘은 CSE 없이 빠르게, 플랫폼은 실제 트래픽으로 각각 검증할 수 있다.
- 실물 칸도 같은 adapter 규약(리소스·메시지 형식)을 쓴다 → "실물과 가상이 구분되지 않는다"는 시연이 성립.
- 칸마다 방향·층·위치 파라미터를 다르게 줘서 제어 결과가 칸마다 다르게 한다.

## 측정 결과 1차 (2026-09-29, 로컬 PC 8코어·8GB, ACME 2026.05.1 Docker 단일 컨테이너)

`tools/scale_smoke.py` (AE 등록 → CNT → CIN, 요청 3건/칸). 세 번을 같은 CSE에 연속 실행해 리소스가 누적된 상태.

| N | 동시 워커 | 성공 | 소요 | 처리량 | CIN p50 / p95 |
|---|---|---|---|---|---|
| 10 | 5 | 10/10 | 0.2s | 175 req/s | 27 / 41 ms |
| 100 | 10 | 100/100 | 2.2s | 137 req/s | 87 / 122 ms |
| 1,000 | 20 | 1000/1000 | 84.3s | **36 req/s** | 629 / 1,344 ms |

측정 직후 ACME 메모리는 112MiB였다. 메모리가 아니라 처리 속도가 병목이다.

`tools/locustfile.py` 동작 확인: 칸 50개, 조도 5초 주기, 45초 실행. 실패 0건, 약 13 req/s, 조도 CIN p50 72ms / p95 1.9s (AE 1,160개가 이미 쌓인 CSE에서 측정).

해석:
- **AE가 1,000개 수준으로 쌓이면 ACME 처리량이 약 1/5로 떨어진다.** 1만 칸의 조도를 60초마다 보고하면 약 167 req/s가 필요하므로, 이 구성(칸당 AE, 기본 설정 ACME)으로는 부족하다. 원인이 저장소 설정(기본 DB, 로그 수준)인지 칸당 AE 구조인지는 아직 구분하지 못했다.
- 다음 비교 대상: (1) ACME 로그 수준·저장소 설정 조정, (2) zone당 AE + 칸당 container 구조, (3) tinyIoT/Mobius에 같은 스크립트.
- 한계: 클라이언트와 CSE가 같은 PC에 있다. 매 실행 전 CSE를 초기화하지 않았다.

## 측정 결과 2차: 설정 × 저장 구조 비교 (2026-09-29)

`sh tools/bench_acme.sh 1000 3000`. 조합마다 새 컨테이너(빈 DB)에서 칸 1,000개를 설치한 뒤 CIN 3,000건을 씀. 동시 워커 20, 조합당 1회 측정. 원본: `results/bench_acme_*.txt`

| 설정 | 구조 | 설치 처리량 | 운영 처리량 | 운영 CIN p50 / p95 |
|---|---|---|---|---|
| 기본 (tinydb, 로그 info) | 칸당 AE | 40 req/s | 10 req/s | 1,757 / 4,139 ms |
| 기본 | zone당 AE | 15 req/s | 7 req/s | 2,411 / 5,005 ms |
| 로그 off | 칸당 AE | 25 req/s | 12 req/s | 1,460 / 2,993 ms |
| 로그 off | zone당 AE | 14 req/s | 8 req/s | 2,464 / 4,464 ms |
| **메모리 DB + 로그 off** | 칸당 AE | **91 req/s** | **78 req/s** | **244 / 372 ms** |
| 메모리 DB + 로그 off | zone당 AE | 90 req/s | 72 req/s | 265 / 417 ms |

해석:
1. **병목은 저장소(tinydb 파일 DB)다.** 메모리 DB로 바꾸면 운영 처리량이 약 8배(10 → 78 req/s)가 된다. tinydb는 리소스 전체를 JSON 파일 하나(측정 중 약 3MB)에 담고 계속 다시 쓴다.
2. **로그 끄기는 효과가 없다.** 차이가 측정 오차 수준이다(1회 측정이라 ±30% 정도는 흔들린다고 본다).
3. **zone당 AE 구조는 성능 이득이 없다.** tinydb에서는 오히려 느렸고, 메모리 DB에서는 차이가 없다. AE 개수가 아니라 전체 리소스 개수가 비용을 정한다. → 구조는 성능이 아니라 **관리 관점**(권한, 일괄 제어, 등록 절차)으로 고른다.
4. 부하 중 ACME CPU는 약 100%(코어 1개)로 고정됐다. 파이썬 단일 프로세스 한계라서 메모리 DB에서도 78 req/s가 천장이다.
5. 필요량과 비교: 1,000칸 × 60초 주기 = 약 17 req/s → 메모리 DB면 충분. 1만 칸 × 60초 = 약 167 req/s → ACME로는 불가.

프로젝트 영향:
- **본 프로젝트는 Mobius 기반이므로, 이 수치는 "ACME의 한계"이지 PolaGrid 플랫폼의 한계가 아니다.** 같은 스크립트를 Mobius(Node.js + MySQL)에 돌려야 발표용 수치가 된다.
- 메모리 DB는 재시작하면 데이터가 사라져 운영용이 아니다. 시뮬레이션 전용 CSE에만 쓸 수 있다.
- 저장소가 병목이라는 결론은 Mobius에도 적용될 가능성이 크다 (MySQL 인덱스, CIN 보존 개수 `mni` 제한이 핵심 변수가 될 것으로 예상, 미측정).
